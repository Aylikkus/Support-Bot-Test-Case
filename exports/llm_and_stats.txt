● Incoming text messages now go through Ollama and are handled by the model's
  ok, partial or error answer. The full suite passes (51 tests). The tests use a
  fake LLM client, so I never called the real Ollama API.

  What happens to each message
  - ok: the bot sends the model's msg and closes the request with
    forwarded_to_operator = false. If Telegram delivery fails, the request stays
    open instead of closing.
  - partial: the bot sends the model's msg and keeps the request open. On the
    next message, the request's earlier messages are sent to the model as a
    user/assistant history. The history is capped at 20 messages and leaves out
    operator messages. Earlier bot replies are replayed as
    {"status":"partial","msg":...}.
  - error: the request is marked forwarded (forwarded_to_operator = true,
    forwarded_at set) and the user gets "Здравствуйте! Ваше сообщение направлено
    оператору, подождите пожалуйста. Время работы операторов с 9:00 до 18:00 в
    будние дни."
  - Unusable output: invalid JSON, an unknown status, a missing or empty msg, or
    a msg over 4096 characters all count as error. A markdown fence around the
    JSON is accepted. The reply is sent as plain text with no parse_mode.
  - Ollama failure: a timeout, a non-2xx response or a missing key is logged and
    also counts as error, so the request goes to an operator.
  - Already forwarded requests: later messages are stored but get no automatic
    reply and no LLM call.
  - Photos and documents: forwarded to an operator without asking the model,
    since it only sees text.

  The prompt
  $DMY_TAG is filled with the current date in Moscow time, in Russian, for
  example 01 октября 2026. $RULES_TAG is filled from promo-rules.md. Both are
  built on every call.

  Code layout
  - Provider isolation: the app depends on a LlmClient interface in
    app/Services/Llm/, and only OllamaClient knows about Ollama. It posts to
    {url}/api/chat with stream: false and format: "json".
  - Answer handling: SupportAnswer::parse() validates the model output, and
    SupportAssistant builds the history and calls the client.
  - Handler: IncomingMessageHandler was rewired to use them, and
    SupportRequestService gained forwardToOperator().
  - Config: config/services.php has an ollama block (key, URL, model, timeout).
    I added optional OLLAMA_MODEL, OLLAMA_URL and OLLAMA_TIMEOUT, defaulting to
    https://ollama.com, gemma4:31b and 60 seconds. OLLAMA_MODEL is in
    .env.example as a comment.
  - Tests: I updated IncomingMessageHandlerTest.php, since the old fixed reply
    "Ваше обращение учтено" no longer exists, and added OllamaClientTest.php.

  Things to know
  - Prompt typo: the JSON examples in system-prompt.md are missing a comma after
    "status": "ok". The model may copy that into its output, which would be
    invalid JSON and get forwarded to an operator. I left your file alone; it's
    worth adding the commas.
  - Blocking calls: the model call runs inside the telegram:poll loop, so a slow
    answer delays other users' updates by up to the 60-second timeout.

● Good suspicion — but from the data you pasted, PostgreSQL is probably working 
  correctly.

  Why you see 00 ч 00 м

  For your sample:

  - request 1: 11:41:57 - 11:41:37 = 20 sec
  - request 2: 11:43:16 - 11:43:03 = 13 sec
  - average = (20 + 13) / 2 = 16.5 sec

  Your UI currently formats only hours + minutes (no seconds), so 16.5 sec
  becomes 00 ч 00 м.

  ---

  Run these SQL checks directly in psql:

  -- 1) Bot-closed count
  SELECT COUNT(*) AS bot_closed_count
  FROM requests
  WHERE status = 'closed'
    AND forwarded_to_operator = false;

  -- 2) Forwarded count
  SELECT COUNT(*) AS forwarded_count
  FROM requests
  WHERE forwarded_to_operator = true;

  -- 3) Per-request first operator response time in seconds
  WITH first_operator_message AS (
      SELECT request_id, MIN(created_at) AS first_operator_message_at
      FROM messages
      WHERE sender_type = 'operator'
      GROUP BY request_id
  )
  SELECT
      r.request_id,
      r.forwarded_at,
      f.first_operator_message_at,
      EXTRACT(EPOCH FROM (f.first_operator_message_at - r.forwarded_at)) AS
  response_seconds
  FROM requests r
  JOIN first_operator_message f ON f.request_id = r.request_id
  WHERE r.forwarded_to_operator = true
    AND r.forwarded_at IS NOT NULL
    AND f.first_operator_message_at >= r.forwarded_at
  ORDER BY r.request_id;

  -- 4) Average response in raw seconds (this is the key truth metric)
  WITH first_operator_message AS (
      SELECT request_id, MIN(created_at) AS first_operator_message_at
      FROM messages
      WHERE sender_type = 'operator'
      GROUP BY request_id
  )
  SELECT
      AVG(EXTRACT(EPOCH FROM (f.first_operator_message_at - r.forwarded_at))) AS
  avg_seconds
  FROM requests r
  JOIN first_operator_message f ON f.request_id = r.request_id
  WHERE r.forwarded_to_operator = true
    AND r.forwarded_at IS NOT NULL
    AND f.first_operator_message_at >= r.forwarded_at;

  -- 5) Emulate current UI formatting (HH + MM only)
  WITH first_operator_message AS (
      SELECT request_id, MIN(created_at) AS first_operator_message_at
      FROM messages
      WHERE sender_type = 'operator'
      GROUP BY request_id
  ),
  avg_data AS (
      SELECT COALESCE(
          AVG(EXTRACT(EPOCH FROM (f.first_operator_message_at -
  r.forwarded_at))),
          0
      ) AS avg_seconds
      FROM requests r
      JOIN first_operator_message f ON f.request_id = r.request_id
      WHERE r.forwarded_to_operator = true
        AND r.forwarded_at IS NOT NULL
        AND f.first_operator_message_at >= r.forwarded_at
  )
  SELECT
      avg_seconds,
      LPAD(((ROUND(avg_seconds)::int / 3600))::text, 2, '0') || ' ч ' ||
      LPAD((((ROUND(avg_seconds)::int % 3600) / 60))::text, 2, '0') || ' м' AS
  hh_mm
  FROM avg_data;
