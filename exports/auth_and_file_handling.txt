  Problems and solutions

  1. Rule conflict: "Do not modify database schema"

  Migrations for these changes are required, and the rule forbids them. I'll
  treat the new schema as the authorized target, but you should reword the rule.
  For example: "Schema is defined in CLAUDE.md; don't deviate from it without
  asking."

  2. operators doesn't fit Laravel auth

  - Laravel's EloquentUserProvider expects a password column, but this table has
    password_hash. The Authenticatable model must override getAuthPassword().
    Hash::check then works as usual.
  - The table has no email or username, and name isn't unique. Login by name is
    ambiguous. Add a unique index on name. This is an index, not a column.
  - There is no remember_token. That's fine if you skip "remember me".
  - The model needs $primaryKey = 'operator_id', and getAuthIdentifierName()
    follows from that.
  - Add a new guard and provider in config/auth.php, e.g. operator. The default
    users table becomes dead weight. Drop its migration or leave it unused.
  - The sessions.user_id column is a bigint, which works for operator_id. If
    sessions are cookie-based and SESSION_DRIVER=database, it will point at
    operators.
  - There is no operator seeding path. You need an artisan command or seeder,
    otherwise nobody can log in. Don't hardcode credentials. Read them from env
    or prompt for them.

  3. messages.user_id is ambiguous

  It is BIGINT NULL with no FK. It now has to mean three things:
  - the Telegram user id when the sender is a user
  - null for the bot
  - either an operator_id or a null for an operator

  Mixing Telegram IDs (large, up to ~2^52) with operator IDs (small serials) in
  one column is a collision risk and can't have an FK.

  Solution: within the fixed schema, define a rule. For sender_type='operator',
  user_id holds operator_id. Always interpret it together with sender_type, and
  never join on it blindly. Document this in CLAUDE.md. A cleaner design would
  be a separate operator_id FK column, which needs your approval since it
  changes the schema.

  4. telegram_message_id for operator messages

  It is NOT NULL. Operator replies go out through the bot, so a Telegram message
  id exists only after sendMessage succeeds. Bot messages too: the id comes
  from the API response. This forces "send to Telegram first, then insert". A
  failed send leaves no record, and a failed DB write after a successful send
  leaves an orphan Telegram message.

  Solution: insert only after a successful API response, and log failures.
  Alternatively, make it nullable, which is a schema change.

  Also, telegram_message_id is unique only per chat. Add a composite unique
  index on (request_id, telegram_message_id), or at least a non-unique one. It
  prevents duplicate rows when Telegram retries a webhook. Webhook idempotency
  matters.

  5. Consistency between message_type, text and image_url

  Nothing enforces that image rows have image_url or that text rows have text.
  Both text and image_url are nullable.
  - A CHECK constraint is cleanest, but it needs a migration. Otherwise enforce
    it in a single Message factory or DTO.
  - The file type has no column for file data. image_url is the only storage
    column, so documents would be stored in a column named "image". Either use
    image_url for both and document that, or add a column (schema change).
  - Photo captions go in text, so an image row can have both fields. This is
    normal, so the rules shouldn't forbid it.
  - You lose the original filename, MIME type and size for files. These matter
    for downloads and display. Without columns, they can only be derived from
    the stored path.

  6. image_url must hold a storage path, not a URL

  Your rules say images are stored locally via Flysystem, served through a
  backend proxy, and visible only to authorized operators. The Telegram file URL
  contains the bot token, so it must never be stored.
  - Store a relative disk path such as requests/12/abc.jpg in image_url. The
    column name is misleading, so document it.
  - Add an operator-guarded route, such as GET /media/{message}, that streams
    from the private disk with auth:operator.
  - Use a private disk, not public, so there's no storage:link bypass.
  - Download the file at webhook time (Telegram file_id links expire). Do it in
    a queued job so the webhook returns fast.
  - file_id isn't stored, so a failed download can't be retried from the DB.
    Keep the retry in the job payload.
  - Validate size, extension and MIME type from the content (not the client).
    Generate the file name yourself, never reuse Telegram's.
  - Content-disposition headers matter for non-image files. Serve with nosniff.

  7. Request lifecycle and indexing

  - user_id is not unique, and there is no rule for how many open requests a
    user may have. Decide it. Typically it is one open request per user, so
    incoming messages attach to it. Enforce it with a partial unique index in
    PostgreSQL: UNIQUE (user_id) WHERE status='open'. This protects against
    races from concurrent webhooks.
  - Add indexes on messages.request_id (Postgres doesn't auto-index FKs),
    requests(status, created_at) and requests.user_id.
  - forwarded_to_operator is derivable from forwarded_at IS NOT NULL, so the two
    can drift. Update them together in a transaction.
  - Operators who close a request aren't recorded. There's no closed_by, no
    assignee and no audit trail. This may be acceptable.

  8. Enum handling

  Laravel's enum() on Postgres creates a varchar with a CHECK constraint. Adding
  a value later means dropping and recreating the constraint. Use PHP backed
  enums (SenderType, MessageType) and cast them. RequestStatus already exists.
  The migration for sender_type needs a CHECK rewrite, so it is easier to write
  the new migration as a table alteration than to edit the existing one.

  9. Migration strategy

  The existing migrations are dated 2026-09-30 and haven't shipped, so you can
  either edit them in place or add new ones.
  - Add new alter migrations if any environment already ran them.
  - Edit in place and run migrate:fresh if nothing is deployed yet. This is
    cleaner.

  Also note that text was NOT NULL. Existing rows are fine, since dropping NOT
  NULL is safe.

  10. LLM and security rules touching this schema

  - Bot messages (sender_type='bot') are presumably LLM-generated. Store them
    only after validation, not the raw output. That follows "never trust raw LLM
    output".
  - Message text is untrusted user input. Escape it when rendering to operators
    (Blade escaping, no {!! !!}), and set parse_mode carefully when relaying.
  - Password hashes: use Hash::make, and make sure password_hash is hidden in
    the model's $hidden.

  Summary of what I'd do next

  1. Update the "Do not modify schema" rule.
  2. Write migrations for the 5 deltas, plus the indexes in 4 and 7, as CHECK
     constraints or partial indexes.
  3. Create the Operator model (guard, getAuthPassword) and a seed command.
  4. Add SenderType and MessageType enums.
  5. Add the private-disk media proxy and an operator-only route.

  Questions that change the plan:
  - May I add the indexes and the unique constraint on operators.name? They
    don't add columns.
  - May I add operator_id to messages, and a file_name/mime column for files?
    Both would deviate from the documented schema.
  - Should migrations be edited in place, or added as new ones?
