  Version-specific traps the doc calls out
  - Api::VERSION says 3.12.0 although the package is 3.16.0.
  - The default config registers HelpCommand, so an unknown /command falls back
    to the help reply.
  - A missing TELEGRAM_BOT_TOKEN doesn't throw. The SDK falls back to the
    placeholder YOUR-BOT-TOKEN, so the token needs explicit validation.
  - The SDK has no webhook route, no secret-token check, and no callback-query
    router. deleteWebhook() takes no parameters.
  - getWebhookUpdate() reads php://input. In a controller it's safer to build
    the update with new Update($request->all()).
  - Update::getMessage() and getChat() return possibly empty Collections, never
    null.
  - Newer update types such as message_reaction and business updates have no
    typed support.
  - reply_markup must be a Keyboard object or a JSON string. A raw nested array
    is not encoded and breaks.
  - Bot API methods without a wrapper (for example sendMessageDraft and
    setChatMenuButton) can still be called through $api->post().

  __toString, the file-id detection regex, and that setWebhook passes extra keys

  How it works
  - The bot receives messages by long polling (php artisan telegram:poll), so it
    needs no public HTTPS URL and no ngrok. I picked this because it's the only
    option that works with a plain docker compose up. A webhook can be added
    later.
  - A private-chat text message is saved to messages (sender_type=user) under
    the user's open request, and a new request is created if none is open.
  - The bot then replies "Ваше обращение учтено" and saves that reply as a bot
    message.
  - Non-text messages, group messages and edited messages are ignored. /start is
    treated as an ordinary message and creates a request.
  - If Postgres fails, the update is not confirmed and is retried after a
    3-second pause. If the reply can't be sent (for example the user blocked the
    bot), the stored message is kept and the failure is only logged.
  - Restarting the bot can re-deliver an update it already handled. The handler
    skips messages whose telegram_message_id is already stored for that user, so
    no duplicates are saved.

  Code
  - app/Console/Commands/TelegramPoll.php is the polling loop.
  - app/Services/Telegram/IncomingMessageHandler.php does the saving and
    replying.
  - Two new migrations (requests, messages) follow the schema in CLAUDE.md
    exactly. The tables didn't exist before, so I created them rather than
    changing an existing schema.
  - The models are SupportRequest and Message. I named the first one that way to
    avoid clashing with Laravel's Request.
  - config/telegram.php reads the token from the environment and registers no
    commands, so an unknown /command no longer gets the SDK's help reply.
  - The new tests are in tests/Feature/Telegram.

  Docker and env
  - Dockerfile, docker-compose.yml, docker/entrypoint.sh and .dockerignore are
    new. Compose starts Postgres 17 with a healthcheck and a bot service that
    runs the migrations and then starts polling.
  - .env and .env.example now use Postgres (DB_*) and have an empty
    TELEGRAM_BOT_TOKEN=. Compose overrides the DB host with postgres inside the
    container. I changed your existing .env from sqlite to Postgres, and its
    APP_KEY is unchanged.
  - The token is empty in .env, and .env.example has an empty APP_KEY.

  To run
  1. Put your token from BotFather into TELEGRAM_BOT_TOKEN in .env.
  2. Start Docker and run docker compose up --build.

  What it does
  - Opening http://localhost:8000 shows the queue of open requests on the left,
    oldest first. Each entry has the user id, the last message, the message
    count and the time.
  - Clicking a request opens its history with user and bot messages. The page
    has a reply box (Ctrl+Enter also sends) and a "Close request" button.
  - Replies go to the user in Telegram and are stored as bot messages, since the
    schema only allows user and bot.
  - Closing a request sets status=closed and closed_at, and it disappears from
    the queue.
  - A dot in the sidebar shows whether the live connection is up.

  Live updates
  - I used Laravel Reverb (WebSockets), so the UI updates immediately, not on a
    poll.
  - Every change broadcasts a SupportRequestUpdated event: a new user message,
    the bot's reply, an operator message, or a close. That covers messages
    coming from the bot process too.
  - The page refetches its data when the event arrives. It also refetches after
    a reconnect to catch anything missed.
  - If Reverb is down, the bot and the operator actions still work. The
    broadcast failure is only logged.
  - I tested the path from the backend through Reverb to a WebSocket client with
    a script. The event arrived. I did not test the Vue page itself.

  Docker
  - Compose now runs postgres, a one-shot migrate, reverb, web and bot, all from
    one image. The Dockerfile builds the frontend in its own stage.
  - Ports are 8000 for the UI and 8080 for Reverb.
  - Port 8080 was already in use on this machine. If it is on yours too, set
    REVERB_PUBLIC_PORT=8090 in .env. Compose then publishes Reverb on that port,
    and the browser connects to it.

  Env changes
  - .env and .env.example now set BROADCAST_CONNECTION=reverb and add the
    REVERB_* settings. .env has generated random values, and .env.example has
    placeholders.
  - I added laravel/reverb, laravel-echo and pusher-js. package-lock.json is
    new.
  - I used npm for the install, although the repo has a pnpm workspace file.

  Limitations to know about
  - There is no login. Anyone who can reach port 8000 can read and answer
    requests, and the realtime channel is public. Fine locally, but add auth
    before exposing it.
  - .env.example has an empty APP_KEY. Run php artisan key:generate after
    copying it, or the web pages will fail.
  - The existing ExampleTest now passes because the frontend build exists.

  The page is resources/js/pages/Requests/Index.vue. The backend is
